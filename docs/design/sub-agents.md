# Sub agents

Part of the [design notes](../../DESIGN.md).

Agents are told (skill, Claude memory, `~/.codex/AGENTS.md`) to use `tmux-spawn` wherever they would use a built-in sub agent. Built-in subagents can't be switched off, so this is an instruction, not enforcement.

User settings below also have `@tmux_agents_*` options; environment overrides win. See the [configuration table](../guide.md#configuration).

## Spawning

1. **Refuse if too deep.** For ordinary sub agents, `TMUX_AGENTS_DEPTH` (unset means 0) must be below `TMUX_AGENTS_MAX_DEPTH` (default 2). An ordinary child gets the caller's depth + 1 through the window or split command's `-e`, so a top-level agent can spawn children, and they can spawn grandchildren, which can't spawn further.
2. **Pick the agent kind.** An explicit `claude`, `codex` or Codex profile wins. Profiles are extra Codex accounts in `TMUX_AGENTS_CODEX_HOMES` (`name=CODEX_HOME ...`). Otherwise, in order:
   - `TMUX_AGENTS_KIND`, pinned by `tmux-agents start`, `tmux-spawn` and the Codex wrappers, since Codex runs commands without its own `CODEX_HOME`;
   - `CLAUDECODE` means claude;
   - a `CODEX_HOME` listed as a profile means that profile;
   - the caller pane's `pane_current_command`.
3. **Name the caller** with `suggest_name` if it has no name, so the child can reply.
4. **Name the child.** `--name` is validated and passed through `format_given_name` (new agent kind plus directory prefix, unless `--exact` or the configured exact preference), then made unique with `unique_name` (`-2`, `-3`, ...). Codex profiles use `codex` for this given-name prefix. Without it, `name_for <agent> <cwd>` gives `claude-<dir>-<N>`.
5. **Pick the session.** It is `agents-<project>`, from `agents_session_for`: the git root's basename, `home` for `$HOME`, else the directory's basename. It is created with `new-session -d` on first use. One window per sub agent by default. With `--split`, resolve an exact agent name or pane id using `resolve_pane`, then use `split-window -d -h` (right) or `-v` (below), `-l N%` (default 50%), the caller's directory and the same environment. The existing window is reused; no hidden session is created.
6. **Hand over the task through a file.** The request body goes to a `mktemp` file. The window runs `tmux-spawn --run <agent> <file>`, which reads and deletes it and `exec`s the agent with the text as its first prompt (`claude "<prompt>"` and `codex "<prompt>"` both start interactive with an initial prompt). No shell ever quotes the task, and nothing has to wait for the TUI to be ready before pasting.
7. **Wire it up.** `set-option -p remain-on-exit on` keeps the transcript on the child pane only after it exits. Only hidden windows get `automatic-rename off`; splits preserve the shared window settings apart from the normal agent border labels. The script sets `@agent` and `@parent`, links both ways, and refreshes labels.

What `--run` sets up (hooks, pins and profile setup are shared with `tmux-agents start`; auto mode applies only to spawned agents):

- **Tracking.** Start/spawn mark `@tracked=1` before launch. The first turn-start, turn-end or notify report also marks a pane tracked. Without tracking, rows show `-`, omit worked time and do not infer needs-you; messaging still works.

- **Auto mode.** With `@tmux_agents_sub_auto` / `TMUX_AGENTS_SUB_AUTO` on (the default), new and resumed sub agents, including members, start with `--permission-mode auto` (Claude) or `-c approvals_reviewer="auto_review"` (Codex). With it off, these flags are omitted and agent defaults apply. `tmux-agents start` always keeps agent defaults. Before this, a spawned Codex on a second account fell back to its config default (`user`) and asked about every command, while its parent had been switched to auto review by hand.
- **Codex identity pins.** For Codex (any profile), `--run` passes `-c shell_environment_policy.set.{TMUX_PANE,TMUX,TMUX_AGENTS_DEPTH}` with the new pane's values, so commands the sub agent runs through Codex's shared daemon see its own identity and depth. `codex sandbox` confirmed the override is applied. See [environment](environment.md#codex-runs-commands-in-a-shared-daemon).
- **PATH.** `--run` puts the scripts' own directory first on `PATH`, because the tmux server's environment may predate the user's PATH setup.
- **Profiles.** For a profile it exports that profile's `CODEX_HOME`, and `TMUX_AGENTS_CODEX_HOMES` is passed to the new window with `-e`.

- **`--for OWNER`.** The sub agent belongs to `OWNER`, which must be a peer of the caller (`resolve_peer`): `adopt` connects it to `OWNER` and sets `@parent` to it, and the record's `parent` is `OWNER`. Sub-agent and member depth is always the caller's plus one; the normal maximum depth applies to both. No task goes to the new agent; the task text becomes a brief in a request from the caller to `OWNER`, asking it to introduce itself and send the first task. The new agent's `@activity` says it is waiting for that. Decided by the user: see [docs/decisions](../decisions/README.md).

## Members

`tmux-spawn --member` creates a long-lived member, including with `--split` and `--for`. It sets `@member=1` and saves `member=1` in the session record; records without the field remain ordinary sub agents. Ownership stays in `@parent`, so explicit dismissal still cascades through members and their helpers. Only top-level callers (no `@parent` and no `@member`) can spawn members; the `--for` owner's role does not restrict the caller. Members add one to the caller's depth, including with `--for`, and obey the normal depth limit. Their helpers are ordinary sub agents and add one level normally. Both chain members spawned by a top-level main are depth 1, leaving depth 2 for the worker's helpers. There is no conversion command. See the [members decision](../decisions/2026-10-05-members.md).

## Browsing: `tmux-agents`

- **List.** One two-line entry per sub agent (panes with `@parent`, excluding members unless they need attention), deduped: name, status and parent, then width-limited activity (`@activity`, or "no report yet") and state/worked times underneath. NAME occupies 26 display cells; project-local prefixes shorten to `kind·rest`, and long names keep both ends around an ellipsis. PARENT abbreviates only within the same project. Entries are grouped into a section per project, marked by a `▸ project` line on the first entry of each; a hidden agent's project comes from its `agents-<project>` session, any other pane's from its directory, the way `tmux-spawn` picks it. Sections sort by their most urgent agent. Every entry starts with its pane id and full name (hidden by `--with-nth=3..`), so `{1}` is the pane even on a section's first entry. Entries are separated by `\036` inside the script (bash strings can't hold NUL) and turned into NUL for `fzf --read0`. `ctrl-a` toggles to every named pane. Parent names are looked up from `@parent`; members appear in the all-named-panes view under their project with `member of <owner>` in PARENT. Status is the same as the chip's: `✗ exited`, else `⚠ permission` (`@perm_since` set), else `@state` (`◆ needs you`, `⠿ working`, `○ idle`, or `✓ done`). Rows that need the user sort first.
- **Rebuild budget.** One pane snapshot supplies names, ancestry and attention state. Session records are read in one batch, with one metadata call, and each distinct directory gets one project lookup. In-memory walks and formatting avoid per-agent processes. `tests/list-budget.sh` checks both scopes and initial opens, including selection, against a process budget and a loose median time cap.
- **Initial draw.** fzf starts with empty input and `start:reload` builds the initial rows. On return, the initial reload writes the selected row position to a temporary file before publishing rows; `load:transform` applies it once. The `start` event also starts one preview loop after fzf opens, so no preview worker delays process startup.
- **List mechanics.** fzf exports `FZF_PROMPT` to reloads with both dimensions (`agents · this window> ` or `all · all windows> `). `ctrl-a` transforms the view and remembers `@tmux_agents_list_mode`; `ctrl-t` transforms only the scope. Fresh opens always use this window. The originating client is exported to reloads as `TMUX_AGENTS_LIST_CLIENT`; its active window comes from `list-clients`, not the script's `$TMUX_PANE`. Enter and ctrl-o print the final prompt before accepting so a hidden viewer can pass `--scope`, `--mode` and `--select` back to the list. The ID and full-name fields stay hidden with `--with-nth=3..` but feeds previews and actions.
- **Search.** Native fzf matches only the displayed abbreviated name and the project, with highlighting and no extra filtering process. Space-separated terms match in any order; an original full hyphenated name does not match its project-local short form. The hidden full label is used only for precise return positioning and previews.
- **Window membership.** A snapshot of pane ids, windows and `@parent` links grows the local set from every pane in the client's window to all descendants. This includes visible splits and hidden grandchildren; missing parents and cycles terminate safely. Both named/sub views use the set. Closed records follow recorded parent names through closed ancestors to a live pane and its visible owning window; missing records and cycles exclude them from local scope. Empty local lists retain the header with a ctrl-t hint.
- **Pinned attention.** Live sub agents and members with `@perm_since` or `@state=needs_you`, and any pane with `@msg_waiting_since`, bypass the scope filter and occupy a single `▸ needs you` section, ordered by their displayed permission/message-waiting/attention timestamp, oldest first. Their second line includes the first visible ancestor's `session:index`, project and activity. A visible split uses its own window; a missing, cyclic or entirely hidden parent chain falls back to the original pane's window. They are not repeated under their projects. The chip stays global; message-waiting panes also enter its amber attention counts and focus.
- **Preview.** A header shows the full label, started time, age, total worked, last turn and turn count; legacy start times remain unknown. Below it, fzf previews `capture-pane -ep -J -S -300` with `--preview-window follow`, so it shows the latest output in colour. A preview command runs once per cursor move, so on its own it's a still frame. To keep it live, fzf runs with `--listen` (a random localhost port, passed to its child commands as `FZF_PORT`; this fzf rejects a Unix socket path), and its `start` event launches one `tmux-agents --preview-loop` in the background. While following, it POSTs a native refresh trigger every `TMUX_AGENTS_PREVIEW_SECS` (0.5s). Manual scrolling pauses the loop and disables the trigger; focus or Ctrl-F resumes it. Picker exit stops the loop and removes its state files. A result already in flight can still move the first scroll once on fzf 0.65; see the [accepted limitation](../decisions/2026-10-05-list-layout-and-worked-time.md#preview-scrolling).
- **Enter on a hidden agent.** The switcher runs in a popup, so it schedules a second popup with `run-shell -b "sleep 0.2; display-popup ..."` and exits. That popup runs `tmux-agents --view <pane>`, which attaches a nested client to the pane's session and selects its window. It unsets `TMUX` (required for nesting) but keeps the socket from `$TMUX` and passes `-S`.
- **Back to the list.** `prefix + d` detaches the nested client; `--view` then runs the list again in the same popup with `--select <name>`, which puts the cursor back with `load:pos(N)+unbind(load)` (`start:pos` fires before the rows are read).
- **`prefix + d` in the list** closes it. fzf can't bind a two-key chord, so this is two bindings: the prefix key (read from tmux's `prefix`, e.g. `ctrl-b`) stores `@tmux_agents_prefix_at`, and `d` runs `tmux-agents --prefix-d`, which answers `abort` if the prefix came within 2s and `put(d)` (type a d) otherwise.
- **Enter on a visible pane, or `ctrl-o`.** `switch-client -c <client> -t <pane>`.
- **`ctrl-x`.** Runs `tmux-dismiss`, then fzf reloads the list.

## Done state and cleanup

- **Idle.** Spawning without task text (including `--for`) sets `@state idle`, displayed as grey `○ idle` between working and done. Requests, real turn-start hooks and progress reports start work; turn end leaves idle alone. Plain top-level launches also start idle, while the known initial task from `start chain` starts working. At turn end, a top-level agent (no `@parent`) with nothing pending returns to idle, clears attention and completes its worked-time turn. Pending work keeps it working. See the [decision](../decisions/2026-10-07-top-level-turn-end-idle.md). Reopening a previously completed session retains the existing done state.
- **Marking.** `tmux-ask` sets `@state done` on the sender when it replies to its own `@parent`, and `@state working` on the tracked receiver of a request. Untracked receivers retain `-`.
- **Cleanup.** `tmux-dismiss --done` considers done and exited sub agents, skips members and any subtree containing a member or unfinished descendants with a note, asks y/N on the terminal, and closes eligible subtrees deepest first. The switcher runs it with fzf `execute` on `ctrl-d`, then reloads.
- **Reports don't reopen work.** `tmux-agent-report` sets `working`, except on a `done` agent: a report right after replying ("delivered abc123") is a summary. Seen live: spirit-fire replied, then reported, and the turn end that followed marked it needs you. Only a new request sets a done agent back to working.
- **Requests reopen work; notices don't.** A request to a `done` sub agent sets it back to `working` and adds it to the sender's `@awaiting`; a notice changes neither. Seen live: a parent broadcast a rule ("no reply needed, don't restart") to finished sub agents as a request. They acknowledged locally without `--reply`, and the next turn end marked them needs you, while the parent kept waiting on them. The skill now says to send information as notices. Notices also leave a Claude sub agent's state alone at turn start (the `UserPromptSubmit` hook sees the prompt begin with `[notice from`): otherwise a notice would clear what it reported with `--waiting`, and the turn end after it would mark it needs you. Guessing from the answer's wording ("standing by") was rejected, since it would also hide real unfinished work.

## Closing, and telling the parent

- **Ancestors may close descendants.** `tmux-dismiss --from ME <name>` follows the target's `@parent` chain to ME and refuses ancestors, itself and unrelated panes. Permissions allow only this `--from` form: `Bash(tmux-dismiss --from:*)` and `prefix_rule(["tmux-dismiss", "--from"])`. Plain `tmux-dismiss` and `--done` stay with the user.
- **Subtree closure.** Both agent and user dismissal close every descendant before its parent, list every closed agent and timestamp each session record. `--keep-children` closes only the target and clears its direct children's `@parent`; they are unowned, with their own descendants unchanged.
- **Passive notice.** Before killing a pane, `note_closed` appends its agent ID to every peer's `@closed`, skipping the pane doing the closing. `tmux-peers` renders labels and offers `--ids` for exact identities. Connecting the same agent again clears its ID from `@closed`; a new agent reusing the label does not erase that history.
- **Session records.** One file per agent ID in `${XDG_STATE_HOME:-~/.local/state}/tmux-agents/<server socket>/sessions/`, with `agent_id`, `name`, `kind`, `id` (conversation ID), `dir`, `parent` (agent ID), `parent_name` (display fallback), `depth`, `member` and `closed` (epoch). New agents never overwrite a closed conversation merely by taking its label. Legacy name-keyed records are migrated once; see [durable identity](state-and-protocol.md#durable-agent-identity).
- **Conversation IDs.** Claude takes an ID up front with `--session-id`. Codex's comes from its first `agent-turn-complete` notify; the session-title side thread is filtered out. An agent closed before a conversation ID is recorded is not resumable, but its record can still link descendants to an ancestor.
- **Reopening.** `tmux-spawn --resume NAME` selects the unique closed agent with that label; ambiguity prints candidates and refuses. `--list-closed` shows IDs, names, closed time, parent and project for agents to select with `--resume-id ID`. The reopened pane retains `@agent_id`, gets an available label (`-2`, `-3` if needed), resumes the original conversation with the same hooks, depth and membership, and connects to its owner. Former splits reopen hidden. It starts done unless retried messages start work; redelivery matches its ID, not its label.
- **Closed in the list.** Records are matched to live panes by agent ID. Rows key internally on `closed:<agent-id>`, while the visible name and second line show the label, closed time, parent and project. IDs never appear in visible rows but may appear in the selected closed agent's preview. Enter and ctrl-o reopen by ID, and ctrl-x deletes only that ID's record. Closed members share this section. The closed section is newest first, within the configured retention period; scope follows parent IDs through records to a live pane.

## Status chip

### Placement

tmux can't float a widget over the panes without stealing focus (popups are modal), so the chip is a second status line.

- `tmux-agents --chip-layout on` (run by `tmux-spawn`) saves the user's `status-format[0]` in `@tmux_agents_main_format`, moves it to `status-format[1]`, puts the chip in `status-format[0]` and sets `status 2`.
- The chip emits `#[align=centre]` itself. Left focus with right counts, and the whole line right-aligned, were tried first.
- When the chip finds no sub agents or panes needing attention it runs `--chip-layout off`, which restores the user's line and `status on`.
- `status-interval 1` keeps the spinner moving.

### Frame rate

tmux re-runs `#()` at most once a second (`status-interval` is whole seconds), so a smooth spinner needs a push model.

- With `@tmux_agents_chip_fps` above 1 (default 10), `status-format[0]` is `#{@chip}`, and `chip_layout` starts `tmux-agents --chip-daemon` with `run-shell -b`, one per server (`@tmux_agents_chip_pid`).
- The daemon rebuilds the chip once a second with `CHIP_SPIN=@@SPIN@@`. Every frame swaps in the next spinner character, sets `@chip` and runs `refresh-client -S` for each client. Measured around 8 to 9 frames a second at 10, because each frame's tmux calls add to the sleep.
- It exits when `status-format[0]` no longer shows `@chip`, which happens when no sub agents or panes needing attention remain.
- It runs with `errexit` off and logs to `/tmp/tmux-agents-<uid>/chip-daemon.log`. Under the script's `set -e`, one failed `refresh-client` (a client detaching mid-loop) killed it, and the chip froze on a stale frame.
- `status-format[0]` also carries `#(tmux-agents --chip-ensure)`, which prints nothing and restarts the daemon within a second if it died. Daemons that start in the same second register their pid, wait 0.3s, and all but the last one registered exit.
- With fps 1, `status-format[0]` is `#(tmux-agents --chip)`, re-run by tmux each second.

### Content

- **Focus.** One agent, rotating every 4s through all sub agents, or only through those that need the user (permission or needs you) if any. Permission waits render white on red, needs you black on amber (`colour214`). Either gets `blink` once it has waited longer than `TMUX_AGENTS_BLINK_SECS` (60s), counted from `@perm_since` or `@attention_since`.
- **Members.** Excluded from ordinary rotation and working/idle/done/exited counts. Permission, needs-you and message-waiting attention still enters the chip's focus and attention counts.
- **Counts.** Per project: `⚠` needs permission, `◆` needs you, `⠹` working (the spinner), `✓` done, `✗` exited.
- **Shortening.** Projects drop `agents-`/`projects-` and cap at 10 characters. Task names over 18 characters keep their start and end around `…`.

### Data, not screen scraping

A first version parsed `capture-pane` output (Claude's spinner and `⏺ Tool(...)` lines, Codex's `• Working` and `• Ran` lines). It was dropped as brittle across TUI versions. Now the chip reads pane options:

- **`@activity`.** The sub agent reports a few words with `tmux-agent-report --from ME "..."`. `tmux-spawn` adds the instruction to every task, and the skill repeats it.
- **`@state done`.** Set by the reply to the parent.
- **`@perm_since`.** Hooks report permission waits, since a blocked agent can't.
  - **Claude:** `tmux-spawn --run` passes `--settings` with `Notification` (`permission_prompt`) → `--perm on --pane <id>`, and `PostToolUse`/`UserPromptSubmit`/`Stop` → `--perm off`. Claude runs hooks in its own process and doesn't ask to trust them, so the pane id can sit in the command.
  - **Codex:** no hooks. With the default `sub_auto=on`, sub agents run with `approvals_reviewer = "auto_review"`, so every `require_escalated` request goes to a review model, and a rejection goes back to the agent, which asks the user in conversation if it must. The user never gets an approval prompt.
  - **Why Codex has no hooks.** An earlier version hooked `PermissionRequest` and turned the chip red on every escalation. The review approved within seconds, but in Codex's code mode the inner command often fired no `PostToolUse`, so the flag stayed until the turn's `Stop`: a sub agent running tests showed NEEDS PERMISSION for minutes with nothing to approve. Dropping the hooks also removed Codex's "hooks are new or changed" trust prompt, which had stopped every new sub agent. Notes if hooks are ever needed again: Codex records hook trust against a hash of the command (so per-pane commands meant a prompt per agent); hooks don't get `shell_environment_policy` (a `codex exec` probe saw the process's own `TMUX_PANE`); the hook input does carry `session_id`, and `UserPromptSubmit` carries the prompt text.
- **`@state needs_you`.** A sub agent or member ended its turn neither done nor waiting on anyone. This is how a Codex sub agent asks the user for something: with `auto_review` it never shows an approval prompt, and it is told to explain what got blocked and ask. `tmux-agent-report --turn-end` decides:
  - done stays done;
  - idle agents, like done agents, return without needing the user;
  - if the agent has live sub agents that aren't done, or agent IDs in `@awaiting` (requests it sent without a reply yet), it shows `waiting for ...` and stays working, because the skill tells agents to end their turn after delegating;
  - the same goes for background work or waiting on another agent. `tmux-agent-report --waiting "<phrase>"` stores `@waiting_on`, cleared by the next normal report, new request or non-notice turn start. A notice to the sender's own parent also sets `@waiting_on` to a parent notice marker; notices to other peers do not. A reply still takes precedence by marking the sender done. For Claude, `claude_background` also counts the children of the pane's claude process that were started through Claude's shell snapshot (`/.claude/shell-snapshots/`), excluding the hook's own ancestors. At `Stop` no foreground command is running, so any such child is a background task; this caught a Claude waiting on a background test run that was showing needs you. Codex's background terminals run in its shared daemon and can't be attributed, so Codex relies on `--waiting`;
  - with nothing pending, a top-level agent (no `@parent`) goes idle and clears `@attention_since`;
  - otherwise the sub agent or member gets `needs_you` and `@attention_since`.

  `needs_you` is cleared by a progress report, an incoming request, or Claude's `UserPromptSubmit` (`--turn-start`).
- **Turn ends.** Claude: the `Stop` hook. Codex: `notify`, which is not a hook, so there is no trust prompt. It receives JSON with `thread-id` and the turn's `input-messages` (checked with a `codex exec` probe), and runs with the daemon's environment like hooks do. The first message is the spawn request `[request from X to NAME via tmux-ask]`, so `--codex-notify` stores the thread id on NAME's pane (`@codex_thread`) and finds the pane by it on later turns. This replaces the user's own `notify` for sub agents only.
- **`@awaiting`.** `tmux-ask` adds the receiver's agent ID on a request and removes the replying agent's ID from its peer's list on a reply. State reports resolve IDs to current labels; agents no longer live are dropped at turn end.

## Alerts

The `alert-bell[42]` hook runs `tmux-agents --alert #{session_name} #{window_name}`. For sessions named `agents-*`, it shows `agent <name> needs you (prefix + a)` for 5s on every client that isn't itself viewing an agents session. Bells in unattached sessions still set `window_bell_flag` and fire the hook, which was verified. Codex rings the bell at the end of every turn, so a bell alone doesn't mean the task finished or that the agent is blocked.
